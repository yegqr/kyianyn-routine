# airalerts: чи буде атака на Київ у наступні 3 години

Проєкт для другого етапу KSE AI Agentic School ([завдання](docs/ASSIGNMENT.md)): аналіз і прогноз повітряних тривог як часового ряду. Ми зібрали погодинні дані про місто Київ з 2026-05-01 до 2026-10-10: 17 публічних Telegram-каналів, офіційні тривоги, погоду, сонце й місяць, символічні дати, політичні події, удари по Росії. Пости розмітила мовна модель Jev, мітки перевірили незалежні джерела, а витік майбутнього ловлять тести. До цих даних ми по черзі поставили чотири питання (епохи): кожне наступне з'являлось, коли попереднє давало відповідь, з якою людина нічого не може зробити. Підсумок: тиші гарантувати не можна, але модель чесно каже, ризик зараз нижчий чи вищий за звичайний, і ці рівні втримались на свіжому тестовому періоді. Код писав і перевіряв Claude Code з агентами; користувач ставив питання, ухвалював рішення і сумнівався в результатах.

## Коротко

| Епоха | Питання | Відповідь на тесті (6 тижнів з 2026-08-29) |
|---|---|---|
| 1. Удари | ракетний удар по Києву в наступні 3 год, щогодини | нічні атаки моделі ловлять, коли вони вже починаються (7 з 9 атак); обидві денні атаки пропущено; надійно кращої за просту частку за 7 днів немає |
| 2. Ночі | о 22:00: спати в коридорі чи в кімнаті | не передбачити: фіналіст попередив про 2 з 7 ракетних ночей; тримається лише «ніч після атаки тиха» (6 з 7) |
| 3. Спокій | чи будуть наступні 3 год тихими, дрони враховано | гарантувати тишу не можна, але «швидше тихо» було правдою у 83% випадків і на розробці, і на тесті |
| 4. Важливість | що найбільше впливає на прогноз і що парсити для живого продукту | хвилі дронів з курсом на Київ, давність атаки, година доби; менша модель не гірша, але джерел для парсингу від цього майже не менше |

## Як запустити

Linux, Python 3.11 або новіший (перевірено на 3.14.4). Версії пакетів зафіксовано в [pyproject.toml](pyproject.toml).

```
python3 -m venv .venv
.venv/bin/pip install -e .
```

Усі команди з кореня репозиторію. Час виміряно 2026-10-11 на цій машині.

| Що | Команда | Час |
|---|---|---|
| тести (72) | `choom -n 500 -- .venv/bin/python -I -m unittest discover -s tests` | 40 с |
| поділ на розробку і тест | `.venv/bin/python -I -m airalerts.evaluation.split` | менше 1 с |
| моделі ударів | `.venv/bin/python -I -m airalerts.strikes.<naive\|share_table\|logistic\|lgbm>` | до 4 с кожна |
| моделі ночей | `.venv/bin/python -I -m airalerts.nights.<rules\|stats\|ml>` | до 13 с |
| моделі спокою | `.venv/bin/python -I -m airalerts.quiet.<baselines\|linear\|trees>` | до 21 с |
| оцінювач ударів | `.venv/bin/python -I -m airalerts.strikes.score final` | 36 с |
| оцінювач ночей | `.venv/bin/python -I -m airalerts.nights.score final` | 3 с |
| оцінювач спокою | `.venv/bin/python -I -m airalerts.quiet.score final` | 57 с |
| прогноз для людини | `.venv/bin/python -I -m airalerts.quiet.forecast ["YYYY-MM-DD HH:MM" \| day YYYY-MM-DD]` | 1.4 с |

- `choom -n 500 --` лише знижує пріоритет процесу для системи, коли бракує пам'яті; без нього команда та сама.
- Спершу моделі питання пишуть прогнози в `data/predictions/` (не в git), потім оцінювач читає їх і рахує всім однакові мірила.
- `final` рахує і тест; так згенеровано три таблиці в [reports/](reports/). Повтор `final` 2026-10-11 відтворив усі три байт у байт. Без аргументу оцінювач рахує лише розробку і **переписує** таблицю в `reports/`; `check NAME` друкує одну модель проти опорної на розробці.
- Таблиці gold лежать у git, silver і bronze ні. Частина тестів (`test_gold_hourly`, `test_nights`) читає silver, тож на чистій копії спершу треба зібрати bronze і silver ([ARCHITECTURE.md](docs/ARCHITECTURE.md), «Як запустити», пункти 1..2). Без кешу відповідей Jev це коштує гроші і дає трохи інші числа ([DATASET.md](docs/data/DATASET.md)).

Приклад прогнозу (`.venv/bin/python -I -m airalerts.quiet.forecast "2026-09-18 17:00"`):

```
Київ, 2026-09-18 17:00: прогноз на 17:00..20:00
  Зараз: тихо.
  Наступні 3 години: швидше неспокійно, високий ризик.
  Ймовірність, що прилетять дрони або ракети: 54%.
  Чому: годин від останньої атаки 1 (+); запуски хвиль дронів за 3 год 10 (+); година доби 17:00 (-).
  Що сталося насправді: неспокійно: дрони, ракети.
```

## Дані

Чому саме так: лише місто Київ, щоб спершу перевірити ідею на одному місті; з травня 2026, бо після масованого обстрілу 14 травня діє новий режим атак ([METHODOLOGY.md](docs/METHODOLOGY.md), розділи 1..2).

| Джерело | Що дає | Як |
|---|---|---|
| Telegram КМВА @VA_Kyiv | тривоги по Києву, початок і кінець до хвилини | публічна сторінка `t.me/s` |
| 7 київських каналів (КМВА, Кличко, монітори) | мітки «ракетний удар», «ракетна загроза», «дрони на Київ» за годинами | `t.me/s` і класифікатор Jev |
| моніторингові канали | сигнали підготовки: стратегічна авіація, МіГ-31К, хвилі ударних дронів (S4) | `t.me/s` і Jev |
| Open-Meteo, модель ECMWF IFS | прогноз погоди з часом видачі | JSON API |
| власний модуль | сонце і місяць над Києвом | код, без мережі |
| таблиця 100 дат, Kremlin, Вікіпедія, Telegram ОП | символічні дати, візити, саміти, переговори | CSV, HTML, MediaWiki API |
| dronestrikemap.com | удари по Росії і запуски по Україні, день відомий через 30 год | JSON API |

Деталі кожного джерела: [PARSING.md](docs/data/PARSING.md). Усього 17 каналів, 163 042 пости з 2026-04-16 ([HANDOFF.md](docs/HANDOFF.md)); 36006 платних викликів Jev, $9.06 ([HISTORY.md](docs/HISTORY.md)).

**Три рівні** ([ADR-0002](docs/adr/0002-data-levels.md)): bronze (джерела як є) → silver (11 таблиць, у кожного рядка `available_at`, коли він став відомим) → gold (таблиця на питання: рядок на момент рішення t, ознаки лише з того, що відомо до t, ціль після t). Заморожена версія gold з контрольними сумами: [DATASET.md](docs/data/DATASET.md).

| Таблиця gold | Епоха | Рядки | Ціль | Частка цілі на розробці |
|---|---|---|---|---|
| `kyiv_hourly` | 1 | 3909 годин | ракетний удар у [t, t + 3 год) | 107 з 2890 (3.7%) |
| `kyiv_nightly` | 2 | 159 ночей | ракетний удар з 22:00 до 08:00 | 23 з 117 (19.7%) |
| `kyiv_quiet` | 3, 4 | 3909 годин | дрони, ракетна загроза чи удар у наступні 3 год | 975 з 2890 (33.7%) |

**Перевірка** ([VERIFICATION.md](docs/data/VERIFICATION.md)):
- тест на витік: для 50 випадкових моментів t ознаки, пораховані лише з того, що було відомо до t, збігаються з gold: 2400 значень, 0 розбіжностей (`tests/test_gold_hourly.py`, вивід запуску 2026-10-11);
- зовнішня перевірка мітки удару незалежними джерелами (офіційні підсумки, новини, дані про пуски) і сигналів іншою моделлю ([ADR-0006](docs/adr/0006-external-verification.md));
- аудит перед моделюванням ([ADR-0007](docs/adr/0007-audit-before-modelling.md)): усі колонки gold перераховано простими циклами без коду модулів на всіх 3909 годинах, 0 розбіжностей; 561 тривогу заново розібрано з постів, збіг до секунди; прочитано пости кожної з 77 годин удару, 15 хибних виправлено вручну (рядків з ударом 151 → 138).

**Відомі вади** ([DATASET.md](docs/data/DATASET.md)): дронова мітка правильна приблизно у 80% (20 з 25 прочитаних годин); одна тривога склеєна і в даних триває 17.6 год; ручні виправлення мітки зроблено після подій, у живому продукті їх не буде.

**Поділ і правила** ([ADR-0008](docs/adr/0008-time-split.md)): тест це останні 6 тижнів, з 2026-08-29 12:00 за Києвом; його відкривали один раз на кожне питання. Усе обирали на розробці: 8 тижневих фолдів з 2026-07-04, модель вчиться на минулому і прогнозує наступний тиждень. Наперед задані правила: до 6 варіантів налаштувань на модель, список до запуску; фіналіст з найкращим результатом на розробці, але простіший, якщо він гірший менш ніж на 0.01; поріг за правилом з розробки.

**Мірила простими словами.** BSS: наскільки ймовірності точніші за сталу частку подій, відому на початок тижня; 0 той самий рівень, більше 0 краще. ROC AUC: шанс, що година з атакою отримає вищий прогноз за тиху; 0.5 це монетка. Інтервали в дужках: 95%, bootstrap по добах (для ночей по ночах), 1000 повторів.

## Епоха 1. Удар у наступні 3 години

**Що і чому.** Завдання просить прогнозувати тривоги, але тривога лише передвісник; людині потрібна відповідь про сам удар ([METHODOLOGY.md](docs/METHODOLOGY.md), розділ 1). Тому ціль: ракетний удар по місту Київ (вибухи, збиття, уламки, влучання) у наступні 3 години, прогноз щогодини.

**Дані і моделі.** `kyiv_hourly`, 50 ознак: година, темрява, тривоги, загрози, пауза після удару, сигнали підготовки, погода, дати, політичні події, удари по Росії. Три моделі обрали агенти ([ADR-0009](docs/adr/0009-three-models.md)): `share_table` (частка ударів у схожих годинах), `logistic` (сигнали з вагами), `lgbm` (дерева рішень на 16 ознаках). Опорна `naive_7d`: частка ударів за останні 7 днів.

**Результат** ([strikes_leaderboard.md](reports/strikes_leaderboard.md)). Розробка: 1342 години, 18 атак; тест: 1014 годин, 9 атак.

| Модель | BSS розробка | BSS тест | Атак спіймано, тест | Годин попереджень на тиждень, тест |
|---|---|---|---|---|
| `share_table` | 0.150 [0.087, 0.199] | 0.007 [-0.280, 0.149] | 7/9 | 28.0 |
| `logistic` | 0.114 [0.034, 0.179] | 0.027 [-0.129, 0.097] | 7/9 | 39.1 |
| `lgbm` | 0.101 [-0.016, 0.186] | 0.169 [-0.049, 0.380] | 7/9 | 33.0 |
| `naive_7d` | -0.016 [-0.039, -0.003] | -0.023 [-0.038, 0.005] | 6/9 | 158.2 |

**Чесний висновок** ([ADR-0009](docs/adr/0009-three-models.md)). На розробці всі три моделі кращі за опорну, на тесті жодна не доведено краща: 9 атак замало, інтервали перетинають 0. На розробці й тесті разом (27 атак) усі три кращі, `lgbm` 0.123 [0.024, 0.211]. Усі 7 нічних атак тесту моделі попередили, обидві денні (18.09 о 17:00 і 10.10 о 12:00) пропустили: денних атак у навчанні майже не було. По ночах (`scripts/analysis/strikes_by_night.py`) моделі будять у 30..35 з 35 тихих ночей, а прогноз о 21..23 вгадує ніч як монетка (ROC AUC 0.47..0.56). Це нічний радар реального часу: атаку видно, коли вона вже починається.

**Що змінили.** Користувачу потрібне рішення наперед: о 22:00 обрати, де спати. Звідси епоха 2.

## Епоха 2. Ніч: спати в коридорі чи в кімнаті

**Що і чому.** Один рядок на ніч, рішення о 22:00 за Києвом; ціль: ракетний удар по Києву з 22:00 до 08:00 ([ADR-0010](docs/adr/0010-night-question.md)).

**Дані і моделі.** `kyiv_nightly`, 159 ночей, зібрана лише з погодинного gold. Три агенти мозкового штурму запропонували 12 моделей у трьох модулях: правила, статистика, машинне навчання ([docs/nights/](docs/nights/rules.md)). Правила задано до першої оцінки: поріг попереджає про 80% ракетних ночей розробки; фіналіст за найкращим BSS на розробці.

**Результат** ([nights_leaderboard.md](reports/nights_leaderboard.md)). Розробка: 56 ночей, 16 з атакою; тест: 42 ночі, 7 з атакою.

| Модель | BSS розробка | BSS тест | Атак попереджено, тест | Зайвих ночей у коридорі, тест |
|---|---|---|---|---|
| `refractory` ★ фіналіст | 0.159 [0.013, 0.245] | -0.072 [-0.261, 0.053] | 2/7 | 11/35 |
| `knn` | -0.002 [-0.070, 0.070] | 0.107 [-0.145, 0.277] | 7/7 | 35/35 |
| `naive_7n` опорна | -0.078 [-0.290, 0.052] | -0.102 [-0.245, 0.053] | 6/7 | 34/35 |

**Чесний висновок.** Фіналіст провалився: темп атак упав з 29% ночей у липні й серпні до 17% у вересні й жовтні, а 28 і 29 вересня дві ракетні ночі йшли поспіль. Порядок моделей перевернувся: найгірші на розробці стали найкращими на тесті, бо відправляють у коридор щоночі. Тримається лише одне: ніч після ракетної ночі тиха (розробка 23 з 23, тест 6 з 7). О 22:00 наші дані не відрізняють ракетну ніч від тихої: сигнали, відомі до 22:00, бувають майже щоночі, а атаки починаються о 00..04.

**Що змінили.** Користувач запитав інакше: чи будуть наступні 3 години спокійними, якщо рахувати і дрони. Подій тут набагато більше, і вдень так само часто, як уночі.

## Епоха 3. Чи будуть наступні 3 години тихими

**Що і чому.** Ціль `y_busy_3h`: у будь-яку з наступних 3 годин дрони летять на Київ або вибухають у ньому, ракетна загроза чи ракетний удар ([ADR-0011](docs/adr/0011-quiet-hours.md)). Головна оцінка на годинах «зараз тихо» (тривоги немає, атаки в минулу годину не було): чи протримається тиша.

**Дані і моделі.** `kyiv_quiet`, 3909 годин, додано відповіді Jev на пости минулої години, хвилі дронів з курсом на Київ, годин від останнього дрона. 11 моделей у трьох модулях ([baselines](docs/quiet/baselines.md), [linear](docs/quiet/linear.md), [trees](docs/quiet/trees.md)). Фіналіст за правилом `logit_signals`: логістична регресія на 7 входах (година доби, давність атаки, сигнали про дрони).

**Результат** ([quiet_leaderboard.md](reports/quiet_leaderboard.md)), години «зараз тихо»:

| | Розробка | Тест |
|---|---|---|
| годин, з них неспокійних | 1067, 31% | 412, 71% |
| BSS `logit_signals` | 0.094 [0.045, 0.148] | 0.284 [0.189, 0.370] |
| BSS `naive_7d` (частка за 7 днів) | -0.061 [-0.119, -0.011] | 0.277 [0.013, 0.517] |
| ROC AUC `logit_signals` | 0.684 [0.621, 0.746] | 0.749 [0.594, 0.837] |
| ROC AUC `naive_7d` | 0.472 [0.406, 0.539] | 0.490 [0.374, 0.597] |

Наперед задане правило «тихо в 95% випадків» майже не досягається: моделі називали тихими 0..2% годин розробки, а на тесті фіналіст не назвав тихою жодної години (лише негативний контроль `logit_all_l2` назвав 5, і всі 5 виявились неспокійними).

**Прогноз для людини** ([forecast.md](docs/quiet/forecast.md)): «швидше тихо», «середній ризик» або «високий ризик», ймовірність і три причини. Межі взято лише з розробки: 0.197 (модель попереджає про 80% неспокійних вікон) і 0.300 (верхня третина прогнозів).

| Години «зараз тихо» | Розробка | Тест |
|---|---|---|
| каже «швидше тихо» | 37% годин | 7% годин |
| коли каже «тихо», справді тихо | 83% | 83% |
| попередив про неспокійні вікна | 80% | 98% |
| «високий ризик»: стало неспокійно | 50% | 80% |

**Чесний висновок.** Гарантувати тишу не можна: навіть «швидше тихо» означає приблизно 1 шанс з 6, що прилетить. Високий BSS тесту здебільшого показує, що модель встигає за ростом неспокою; частка за 7 днів має майже стільки ж, і модель не доведено кращою за неї. Але ранжування втрималось (ROC AUC 0.749 проти 0.490), а слова «швидше тихо» тримали зміст. На тесті модель точніша за очевидні правила (з [forecast.md](docs/quiet/forecast.md), ці порівняння не були задані до тесту): BSS 0.284 проти 0.206 у правила «нещодавно була атака», різниця [+0.011, +0.145]; проти 0.178 у правила «година доби і давність атаки», різниця [+0.045, +0.169]. Масовану ракетну атаку від дронів модель майже не відрізняє: «високий ризик» перед ракетним ударом 58% і 100% годин, перед лише дронами 54% і 86% (розробка і тест). Схему рівнів описано вже після відкриття тесту, тож це описовий аналіз, а не перевірка, задана наперед.

**Що змінили.** Користувач хоче живий продукт: збирати дані наживо і оновлювати прогноз на сайті, наприклад кожні 10 хвилин. Чим менше джерел, тим легше парсити. Звідси питання епохи 4.

## Епоха 4. Що впливає найбільше і що парсити наживо

**Що і чому.** Які входи фіналіста `logit_signals` справді несуть прогноз, чи можна парсити менше і чи реально оновлювати кожні 10 хвилин ([importance.md](docs/quiet/importance.md)).

**Як.** Скрипт `scripts/analysis/quiet_importance.py` (лише друк): ваги моделі, внесок кожного входу, перемішування входу (наскільки падає якість, якщо вхід зіпсувати), моделі на групах джерел з правилом вибору, записаним до оцінки, і PCA. Вибір лише на розробці, тест один раз як звіт.

**Результат**, падіння BSS, коли вхід перемішано (години «зараз тихо»):

| Вхід | Розробка | Тест |
|---|---|---|
| хвилі дронів з курсом на Київ за 6 год | 0.056 | 0.072 |
| годин від останньої атаки | 0.042 | 0.027 |
| година доби | 0.040 | 0.000 |
| оцінка Jev «дрони на Київ» за годину | 0.011 | 0.014 |
| постів за годину | 0.005 | 0.004 |
| годин від останніх дронів | 0.003 | -0.005 |
| запусків хвиль дронів будь-куди за 3 год | 0.002 | 0.001 |

Менша модель (час, історія атак, хвилі дронів, без постів) за правилом тримає якість: BSS на розробці 0.091 проти 0.094 у повної, на тесті 0.303 проти 0.284 (тест лише звіт, вибір зроблено на розробці).

**Чесний висновок.** Найбільше важать хвилі дронів на Київ: на тесті вони дають 44% руху прогнозу, на розробці 26%. Година доби допомагала влітку, а на тесті, коли з'явились денні атаки, не дає нічого. Але менша модель майже не зменшує парсинг: викинуті входи рахуються з тих самих каналів і того самого запиту Jev. Для живого продукту потрібні ті самі 10 каналів Telegram і два класифікатори Jev. Оновлювати кожні 10 хвилин технічно можна, статистично ще ні: модель навчена і перевірена лише на повних годинах. Чесний варіант зараз: сторінка оновлюється кожні 10 хвилин (статус тривоги, нові хвилі дронів як текст), а ймовірність щогодини.

**Що далі** (ще не зроблено): живий забір і заміри затримки (скільки секунд відповідає Jev і як швидко пост з'являється на `t.me/s`, не міряли); перевірка 10-хвилинного прогнозу на розробці з правилом, записаним наперед; варіант без Jev на київських каналах; рішення, чи переводити сайт на 5 входів замість 7.

## Висновки

**Що працює.**
- Дані без витоку майбутнього, з трьома рівнями перевірки, відтворювані з кешу; оцінювачі відтворюють таблиці в `reports/` байт у байт.
- Погодинні моделі як нічний радар: 7 з 7 нічних атак тесту попереджено, коли атака починалась.
- Прогноз тиші на 3 години: рівні ризику мали той самий зміст на розробці й тесті, «швидше тихо» правдиве у 83% випадків.
- Просте правило: ніч після ракетної ночі тиха (23 з 23 і 6 з 7).

**Де межі.**
- Атак мало: 9 на тесті ударів, 7 ракетних ночей; інтервали широкі, «краще за опорну» на тесті не доведено жодного разу.
- Режим атак змінюється: восени неспокійних годин 71% проти 31% влітку, з'явились денні атаки, яких модель не бачила.
- О 22:00 ракетну ніч не передбачити; масовану атаку від дронів модель не відрізняє.
- Дронова мітка правильна приблизно у 80%; ручні виправлення мітки є лише в історії.
- Тест епох 2..4 не повністю сліпий: ми вже бачили тестові ночі й знали про неспокійну осінь, тому все обирали лише на розробці і пишемо це застереження.

**Практична цінність.** Прогноз не дозвіл виходити з укриття. Він каже, чи ризик у наступні 3 години нижчий чи вищий за звичайний, з причинами: «зараз хвилі дронів летять на Київ» або «атака щойно була». Офіційна тривога в наступні 3 години після «швидше тихо» була у 17% випадків тесту (5 з 29), після «високого ризику» у 74% ([forecast.md](docs/quiet/forecast.md)). Для живого сайту потрібні 10 каналів і Jev, оновлення щогодини перевірене, а 10-хвилинне треба перевірити окремо.

## Як ми працювали

Оркестратор (Claude Opus у Claude Code) ділив роботу на шматки через Workflow; кожен шматок будував один агент, а приймав свіжий агент лише з читанням: стартував з «не пройдено», сам запускав перевірки, підкладав витік, який тест мусить зловити, і читав рядки вручну. Моделі шукали 4 агенти-дослідники, 2 судді і 3 скептики, для ночей і спокою ще 3 агенти мозкового штурму ([ADR-0009](docs/adr/0009-three-models.md), [HISTORY.md](docs/HISTORY.md)). Правила вибору, пороги і кількість варіантів записували до оцінки, а тест відкривали один раз. Помилки, які ми зловили і виправили: таблиця порівняння спершу показувала тест на кожному запуску, тепер лише через `final`; аудит знайшов 15 хибних годин удару з 77; переписані після публікації пости починали події сигналів на 1.3..5.7 год раніше; звіт таблиці спокою надрукував частку неспокою на всій таблиці разом з тестом (46% проти 34% на розробці), звіт виправлено, а знання записано як застереження; наївна модель виявилась гіршою за сталу частку, бо після удару йде пауза. Головні рішення про дані, пакети і постановку питань ухвалював користувач ([HISTORY.md](docs/HISTORY.md), «Рішення користувача»).
