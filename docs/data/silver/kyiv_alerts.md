# kyiv_alerts

Тривоги по місту Київ як інтервали. Модуль `src/airalerts/silver/alerts.py`, файл `data/silver/kyiv_alerts.parquet`. Правила розбору: [PARSING.md](../../PARSING.md) розділ 1. Рівні даних і контракт: [ARCHITECTURE.md](../../ARCHITECTURE.md).

## Що це

Один рядок = одна тривога по місту Київ: від поста старту до поста відбою. Усього 562 рядки (стан на 2026-10-10T17:11:31Z), з них 16 до T0 (2026-04-17..2026-04-30, потрібні для вікон назад) і 546 від T0. Відкритих тривог немає.

## Колонки

| колонка | тип | опис |
|---|---|---|
| `alert_id` | BIGINT | порядковий номер за `start_utc`, з 1; унікальний |
| `start_utc` | TIMESTAMP (UTC) | час поста старту; для тривоги з латки це час поста eTryvoga |
| `end_utc` | TIMESTAMP (UTC) | час поста відбою; NULL, якщо тривога відкрита в кінці даних |
| `duration_min` | DOUBLE | `end_utc` мінус `start_utc` у хвилинах; NULL, якщо відкрита |
| `max_level` | VARCHAR | найвищий рівень за тривогу: `alert` < `yellow` < `red`; `alert` це старий формат КМВА без рівня |
| `start_source` | VARCHAR | `VA_Kyiv` або `UkraineAlarmSignal` |
| `start_post_id` | BIGINT | id поста старту в `start_source` |
| `end_post_id` | BIGINT | id поста відбою у `VA_Kyiv`; NULL, якщо відкрита |
| `gap_from_prev_min` | DOUBLE | хвилин від `end_utc` попередньої тривоги до `start_utc`; NULL у першої |
| `available_at` | TIMESTAMP (UTC) | рівно `start_utc` |

Склеювання (PARSING 1): старт відкриває тривогу; ще один старт при відкритій тривозі це пояснення або зміна рівня (піднімає `max_level`); відбій закриває. Відбій без відкритого старту бере старт з латки: останній старт Києва в eTryvoga перед відбоєм, пізніший за кінець попередньої тривоги, інакше модуль зупиняється з помилкою. Виняток: перший відбій у даних без старту (перед першою тривогою) закриває тривогу, що почалась до FETCH_FROM; це не тривога нашого періоду, і модуль його відкидає. Старт з eTryvoga для нього береться, лише якщо він пізніший за FETCH_FROM. Відкинуті відбої друкує `main()` у `dropped_end_post_ids`. Відбій і новий старт за кілька секунд чи хвилин лишаються двома тривогами (PLAN: червоний на жовтий з паузою до 2 хв): склеїти пізніше можна за `gap_from_prev_min`.

## Час доступності

- `available_at = start_utc`: тривога відома з поста старту. КМВА постить на 4-5 с пізніше за офіційний канал, але `start_utc` це час саме цього поста, тож витоку немає.
- Кінець відомий лише з `end_utc`. `ASOF["kyiv_alerts"]` у модулі повертає таблицю, якою її знали перед `{t}`: рядки з `available_at < {t}`; якщо `end_utc >= {t}` (або порожній), то `end_utc`, `duration_min`, `max_level` і `end_post_id` стають NULL. `max_level` ховається разом з кінцем, бо відкрита тривога ще може піднятися з жовтого на червоний. Постановка S1 вимагала ховати лише `end_utc`; решта колонок похідні від кінця, тому ховаються теж.
- Кінець даних: ключ `data_until` у метаданих Parquet = час останнього поста VA_Kyiv (2026-10-10T17:11:31Z). `features()` кидає `ValueError`, якщо `t_utc` пізніше: після цього моменту "немає тривог" було б вигадкою. Остання година, яку можна рахувати, 2026-10-10T17:00Z.

## Ознаки для gold

`features(con, t_table)` повертає `pyarrow.Table`: `t_utc` першою, рівно один рядок на кожен різний `t_utc`, далі колонки нижче. Читає лише view `kyiv_alerts`, бере тривоги з `available_at < t_utc`; кінець `end_utc >= t_utc` вважається невідомим (тривога відкрита). Усе в UTC, київської доби немає. Рівні тривоги в ознаки не входять (PLAN).

| колонка | тип | визначення |
|---|---|---|
| `alert_active` | BOOLEAN | є тривога зі `start_utc < t` і (`end_utc` порожній або `end_utc >= t`) |
| `alert_active_min` | DOUBLE | хвилин від `start_utc` активної тривоги до t; 0.0, якщо активної немає |
| `alerts_started_3h` | BIGINT | кількість `start_utc` у `[t - 3 год, t)` |
| `alerts_started_6h` | BIGINT | те саме для `[t - 6 год, t)` |
| `alerts_started_24h` | BIGINT | те саме для `[t - 24 год, t)` |
| `alert_minutes_24h` | DOUBLE | хвилин під тривогою у `[t - 24 год, t)`: для кожної тривоги зі `start_utc < t` довжина перетину `[start_utc, min(end_utc, t))` з `[t - 24 год, t)`; відкрита чи невідома кінцем тривога рахується до t |
| `alerts_7d` | BIGINT | кількість `start_utc` у `[t - 7 діб, t)` |
| `alerts_14d` | BIGINT | кількість `start_utc` у `[t - 14 діб, t)`; вікно повне вже в T0, бо дані починаються з FETCH_FROM = T0 мінус 14 діб |
| `hours_since_alert_end` | DOUBLE | 0.0, якщо `alert_active`; інакше годин від найпізнішого `end_utc < t` до t; NULL лише коли до t не було жодного відбою (для t від T0 не буває) |

Для t від 2026-04-30T21:00Z до 2026-10-10T17:00Z (3909 годин) жодної колонки з NULL.

## Як перебудувати

```
python3 -I scripts/bronze/tg_fetch.py VA_Kyiv data/bronze/telegram/VA_Kyiv.jsonl   # bronze КМВА: дописує лише нове
python3 -I scripts/bronze/va_count.py data/bronze/telegram/VA_Kyiv.jsonl           # відбої без старту (orphan ends)
python3 -I scripts/bronze/etryvoga_patch.py [годин до відбою, типово 3]            # латка, лише якщо список не порожній
.venv/bin/python -I -m airalerts.silver.alerts                                      # silver: data/silver/kyiv_alerts.parquet
.venv/bin/python -I -m airalerts.silver.alerts check                                # самоперевірка
```

Якщо після свіжого забору з'явився відбій без старту, а латки немає, silver зупиняється з повідомленням. Якщо старт далі ніж за 3 години до відбою, запустити латку з більшою кількістю годин.

## Пастки

- Початок даних. FETCH_FROM (2026-04-16T21:00Z) це T0 мінус 14 діб, тож `alerts_14d` повне від T0. Перший збережений пост КМВА має id 17740 і час 2026-04-17T05:59:01Z, перша тривога 2026-04-17T16:54:40Z, і перший пост про тривогу в даних це її старт (пост 17744). Якби першим був відбій, його тривога почалась до FETCH_FROM і не є тривогою нашого періоду: модуль її відкидає (див. Склеювання). Другий відбій без старту підряд, як і відбій без старту далі в даних, зупиняє модуль. `va_count.py` і латка рахують відбої від T0, тож латку для відбою між FETCH_FROM і T0 вони не зберуть (таких немає, Перевірка 1; `check` перевіряє це на кожному запуску).
- Пропущені тривоги. КМВА зрідка не постить тривогу чи коротку перерву (PARSING розділ 1: 2026-06-20 21:52:21Z, 2026-08-29); ці тривоги тут не відновлюються.
- Рівні. `alert` це старий формат без рівня (340 тривог), `yellow` 200, `red` 22. Порядок `alert` < `yellow` < `red` прийнято за порядком переліку в постановці S1 (рішення будівника, не з PLAN); у ознаки gold `max_level` не входить. `max_level` не тримає порядку змін рівня, лише максимум.
- Червоний на жовтий: відбій і новий старт за хвилину це дві тривоги. Пауз до 2 хв чотири (`alert_id` 16, 329, 478, 538), до 5 хв шість (ще 162 і 256); 478 це жовтий на червоний, 538 червоний на жовтий.
- Довгі тривоги: 44 довші за 3 год, 11 довші за 6 год. Тривога триває до поста відбою, тож пропущений відбій зливає дві тривоги в одну.
- Пости, які правило не вважає стартом чи відбоєм, на інтервали не впливають: 19 постів "Увага! У Києві оголошено повітряну тривогу..." і ще 43 пости "У Києві лунає повітряна тривога..." лежать усередині тривог (усі 62); "У столиці оголошено відбій повітряної тривоги" (пост 18246, 2026-05-24T02:50:49Z) вийшов через 578 с після звичайного відбою тієї ж тривоги; 12 нагадувань про роботу ППО лише містять слово "відбій" у тексті (9 "Сили ППО працюють..." чи "Сили ППО продовжують працювати..." і 3 "У столиці працюють сили ППО", пости 19669, 19710, 19764). Усі ці числа друкує `check` у рядках `stats`.
- Відбій рівно в t ще невідомий до t: тривога вважається активною (`end_utc >= t`).
- `alert_id` це номер за часом старту: стабільний, поки нові тривоги лише дописуються в кінець, і зсувається, якщо в bronze з'являться ще давніші дані. Дозабір до FETCH_FROM додав 7 тривог перед колишнім першим постом (2026-04-24T06:00:04Z) і зсунув усі `alert_id` на 7.
- Модуль не ставить `data/airalerts.duckdb`: view на Parquet робить `.venv/bin/python -I -m airalerts.db`.
