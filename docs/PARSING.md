# Парсинг: практичний посібник для агента-парсера

Цей документ описує рівень bronze: сирі дані як є (`data/bronze/`). Рівні silver і gold: [ARCHITECTURE.md](ARCHITECTURE.md). Пошук джерел закінчено. Для кожної категорії даних тут є обране джерело, адреса, спосіб забору, сирий формат, місце зберігання, правила обробки, пастки і перевірка з очікуваними числами. Завдання парсера: забрати сирі дані, структурувати їх і перевірити, не шукаючи нових джерел. Навіщо ці дані, описано в [METHODOLOGY.md](METHODOLOGY.md).

Усі джерела перевірено наживо 2026-10-10: спершу агенти-збирачі, потім окремі агенти-перевіряльники перезапустили рецепти і перерахували числа. Числа в «Перевірці» це стан на 2026-10-10; на пізніший запуск останні id і підсумки будуть більші.

## 0. Загальні правила

- **Період:** від T0 = 2026-05-01 00:00 за Києвом = `2026-04-30T21:00:00Z` до дати зрізу.
- **Старт забору:** `FETCH_FROM = 2026-04-16T21:00:00Z` (T0 мінус 14 діб, рішення користувача 2026-10-10), щоб ознаки з вікном назад до 14 діб були повні вже 1 травня. Погода, астрономія, календар і Kremlin назад не дивляться, тому їх не розширюємо. Сторінки Вікіпедії беремо цілком.
- **Час:** усі мітки часу в UTC, формат `2026-10-10T12:42:56Z`. Київський час рахує лише обробка: до 2026-10-25 це UTC+3, далі UTC+2.
- **Час доступності:** кожен запис має момент, коли він став публічним (`published_at`, `announced_at` або `available_at_utc`). Ознака для прогнозу в момент t бере лише записи з часом доступності < t. Запис без такого часу йде лише в мітку.
- **Сирі дані лише дописуються:** у `data/bronze/` старий рядок не змінюємо і не видаляємо. Похідні таблиці пишемо в `data/silver/`.
- **Повторний запуск** докачує лише нове, а перерваний бекфіл продовжує з місця обриву.
- **Маніфест:** після кожного запуску дописати рядок у `data/bronze/MANIFEST.md`: джерело, час запуску (UTC), записів, перший і останній час.
- **Ввічливість:** один потік на джерело, пауза 1-2 с, повтор із паузою на HTTP 429 і 5xx.
- **Без ключів і реєстрацій.** Токени, реєстрації і нові залежності лише з «так» користувача. Код лише на stdlib Python 3.11+.
- **Безпека:** завантажене не виконуємо, скрипти запускаємо як `python3 -I`.

**Порядок роботи:** (1) Telegram за чергою з 0.1, великі канали у фоні; (2) погода, розділ 3 (кілька хвилин); (3) астрономія, розділ 4 (секунди); (4) `dates.csv`, розділ 5; (5) Kremlin і Вікіпедія, розділи 6 і 8; (6) перевірки з кожного розділу і маніфест.

### 0.1 Telegram: спільний рецепт

Усі 17 каналів з розділів 1, 2, 6, 7 і 8 забираються одним скриптом. Канал, потрібний кільком розділам, качаємо один раз.

**Ендпоінти** (без логіну): `https://t.me/s/<channel>` дає до 20 найновіших постів; `?before=<id>` дає до 20 постів з меншим id. Пошук `?q=<слово>` віддає лише ~20 найновіших збігів, а з `before` дає ще кілька старших і зупиняється: для архіву не годиться.

**Розмітка поста:**

| Поле | Де в HTML |
|---|---|
| межа поста | `<div class="tgme_widget_message_wrap` |
| канал і id | `data-post="<channel>/<id>"` |
| час | `<a class="tgme_widget_message_date" ...><time datetime="2026-10-10T12:42:56+00:00">`, UTC (видимий на сторінці час теж UTC) |
| текст | `<div class="tgme_widget_message_text js-message_text">`; цитата у відповіді має клас `js-message_reply_text`, її не брати |
| перегляди | `<span class="tgme_widget_message_views">55.5K</span>` |
| правка | `<span class="tgme_widget_message_meta">edited &nbsp;<a ...>` |
| репост | `<a class="tgme_widget_message_forwarded_from_name" href="https://t.me/vitaliy_klitschko/7821">` |

**Сирий формат:** `data/bronze/telegram/<channel>.jsonl`, один JSON на пост, `<channel>` точно як у `data-post`. Рядки не відсортовані: читати, прибирати дублі за `post_id` (лишати перший рядок) і сортувати.

| Поле | Тип | Опис |
|---|---|---|
| `channel` | str | канал без @ |
| `post_id` | int | id поста |
| `published_at` | str | час публікації, UTC з `Z` |
| `text` | str | текст без HTML, `<br>` стає `\n`, емодзі лишаються; `""` для поста лише з медіа |
| `edited` | bool | пост змінено після публікації |
| `views` | str або null | перегляди як на сторінці («6.83K») |
| `forwarded_from` | str або null | джерело репосту: `<channel>/<id>` або ім'я автора |
| `url` | str | `https://t.me/<channel>/<id>` |
| `fetched_at` | str | час забору, UTC з `Z` |

Реальний запис (репост ДСНС у каналі КМВА, текст скорочено):

```json
{"channel": "VA_Kyiv", "post_id": 21663, "published_at": "2026-10-10T12:41:00Z", "text": "Внаслідок російської атаки в Оболонському районі постраждали 5 людей, одна з них - у важкому стані. ", "edited": false, "views": "4.24K", "forwarded_from": "dsns_kyiv/5225", "url": "https://t.me/VA_Kyiv/21663", "fetched_at": "2026-10-10T15:53:11Z"}
```

**Скрипт** `tg_fetch.py`. Запуск: `python3 -I scripts/bronze/tg_fetch.py <channel> data/bronze/telegram/<channel>.jsonl` (since за замовчуванням FETCH_FROM, пауза 1.5 с). Друкує підсумок: сторінки, рядки, перший і останній час, min і max id.

**Куди:** `data/bronze/telegram/VA_Kyiv.jsonl`, `data/bronze/telegram/UkraineAlarmSignal.jsonl`.

**Правила обробки:**
- head = текст без початкових емодзі і знаків, перші 120 символів: `re.sub(r"^[^0-9A-Za-zА-Яа-яЄєІіЇїҐґ]+", "", text).strip()[:120]`.
- Відбій: `^(м\.\s*Київ\s*[-–]\s*)?[Вв]ідбій`.
- Старт: `^((м\.\s*Київ\s*[-–]\s*)?[Пп]овітряна тривога|(Червоний|Жовтий) рівень небезпеки|(У Києві |У столиці )?[Оо]голошено повітряну тривогу)`; рівень red, якщо в head є «Червоний», yellow, якщо «Жовтий», інакше alert.
- Нагадування всередині тривоги («У Києві лунає повітряна тривога...», «Сили ППО працюють...», «Загроза БпЛА триває...») не є стартом: regex з `^` їх відсікає.
- Склеювання: старт відкриває інтервал; ще один старт при відкритому інтервалі це пояснення або зміна рівня; відбій закриває. Відбій без відкритого старту йде в латку.
- Формати КМВА: старий («🔴 м. Київ - повітряна тривога!», «🟢 м. Київ - відбій повітряної тривоги!») від 17868 (2026-05-02T06:50:58Z) до 20895 (2026-09-23T02:06:17Z); новий («🟡 Жовтий рівень небезпеки», «🔴 Червоний рівень небезпеки», «🟢 Відбій повітряної тривоги.») з 20477 (2026-09-08T08:02:54Z). З 09-08 до 09-23 формати змішані.
- Латка eTryvoga, лише м. Київ: одиночний пост, де перший рядок без емодзі рівно «Київ», а другий «Червоний рівень тривоги», «Жовтий рівень тривоги» або «Повітряна тривога»; або груповий пост з рядком рівно «• Київ» під заголовком «🔴 Червоний рівень тривоги» чи «🟡 Жовтий рівень тривоги». Не старт: «🚀 Київ / Загроза...» (651294), «⚠️ Київ / ЗМІ повідомляють про вибухи» (651298), «🟡 Відбій червоної тривоги» (це зниження до жовтого). «Троєщина (Київ)» це район, «(Київська обл.)» область. Брати останній старт м. Київ перед e.

**Витік:** старт = `published_at` поста старту, кінець = `published_at` відбою. На момент t відкрита тривога має лише старт. КМВА публікує в середньому на 4-5 с пізніше за офіційний канал.

**Пастки:**
- Відбій без старту за період один: VA 21659 (відбій 2026-10-10T11:35:57Z); старт є в eTryvoga о 10:57:27Z («🔴 Червоний рівень тривоги», «• Київ»).
- КМВА зрідка не постить тривогу взагалі: в official є старт 2026-06-20 21:52:21Z, у КМВА немає поста в межах 20 хв.
- КМВА зрідка не постить коротку перерву: 2026-08-29 у КМВА одна тривога 04:29-08:54Z, в official 04:29-05:29Z.
- Червоний на жовтий: КМВА пише відбій і за хвилину новий жовтий старт (2026-10-07 20:48Z і 20:49Z), у даних це дві тривоги.

**Перевірка:** повний VA_Kyiv з T0 (стан 2026-10-10 14:42Z) має дати `alerts by Kyiv month: {'05': 58, '06': 45, '07': 59, '08': 120, '09': 185, '10': 78} total 545 orphan ends: [21659]`.

Код: [scripts/bronze/va_count.py](../scripts/bronze/va_count.py), запуск `python3 -I scripts/bronze/va_count.py data/bronze/telegram/VA_Kyiv.jsonl`.

**Відкриті рішення:**
- Відбій без старту: брати старт з eTryvoga (пропоную; випадок один) чи лишити тривогу без старту.

## 3. Погода

**Що збираємо:** погодинний прогноз ECMWF IFS HRES 9 км для центру Києва (50.4501, 30.5234): хмарність, опади, вітер (швидкість, пориви, напрям), видимість. Кожен прогін (00, 06, 12, 18 UTC) зберігаємо цілим із часом старту, тож для моменту t беремо лише прогноз, виданий до t.

**Джерело:** Open-Meteo Single Runs API, `models=ecmwf_ifs`, https://single-runs-api.open-meteo.com/v1/forecast. Без ключа; безкоштовно лише для некомерційного використання; дані CC BY 4.0. Архів ECMWF IFS HRES з березня 2024.

Чому не інші (перевірено 2026-10-10): Previous Runs API для `ecmwf_ifs` не має поривів і видимості (0 з 3912 год), видимість там є лише в `ukmo_seamless` і з дірками; `best_match`, `gfs_seamless`, `icon_seamless`, `gem_seamless` без видимості. Historical Forecast API не має часу видачі прогнозу, тобто ризик витоку. OGIMET SYNOP 33345: спостереження раз на 3 год і без часу публікації.

**Як забирати:**
- Один запит = один прогін, 168 погодинних значень від `run`: `https://single-runs-api.open-meteo.com/v1/forecast?latitude=50.4501&longitude=30.5234&hourly=cloud_cover,precipitation,wind_speed_10m,wind_gusts_10m,wind_direction_10m,visibility&models=ecmwf_ifs&run=2026-10-09T12:00&timezone=UTC&format=json`.
- Прогони кожні 6 год від `2026-04-23T00:00` до останнього опублікованого. Останній: `https://api.open-meteo.com/data/ecmwf_ifs/static/meta.json`, поля `last_run_initialisation_time` і `last_run_availability_time` (unix-секунди). 2026-10-10 прогін 06:00 вийшов о 12:22:53 UTC, через 6.4 год.
- Неопублікований або відсутній прогін дає HTTP 400 `{"reason":"The requested model run is not available. ...","error":true}`: пропустити і повторити пізніше.
- Ліміти: до 10 000 викликів на добу, 5 000 на годину, 600 на хвилину. 654 прогони в 4 потоки пройшли за 191 с.

Код: [scripts/bronze/wx_fetch_run.py](../scripts/bronze/wx_fetch_run.py) (stdlib, перевірено). Запуск: `python3 -I scripts/bronze/wx_fetch_run.py data/bronze/weather 2026-10-09T12:00 2026-10-10T06:00`; бекфіл це той самий `fetch_run` у циклі по прогонах.

**Сирий формат і куди:**
- `data/bronze/weather/openmeteo_single_runs/ecmwf_ifs_<YYYYMMDDTHH>.json`: відповідь як є, файл на прогін.
- `data/bronze/weather/ecmwf_ifs_runs.csv`: рядок на пару (прогін, година), колонки `run_utc, valid_utc, lead_h, cloud_cover_pct, precipitation_mm, wind_speed_10m_kmh, wind_gusts_10m_kmh, wind_direction_10m_deg, visibility_m, available_at_utc, fetched_at_utc`. Порожня клітинка = null.
- Одиниці: % , мм (сума за попередню годину), км/год, градуси, м. Приклад (прогін 2026-10-09T12:00, година 2026-10-10T12:00): хмарність 81, опади 0.0, вітер 12.6, пориви 31.7, напрям 227, видимість 45720.

**Правила обробки:**
- Лише `models=ecmwf_ifs` і `timezone=UTC`, координати не міняти. Вузол сітки 50.439365, 30.476192, ~3.6 км на захід від центру.
- Ключ (`run_utc`, `valid_utc`); дублікати від повторного запуску прибрати.
- На `lead_h = 0` опади і пориви порожні. Звичайно прогони 06 і 18 UTC мають 145 непорожніх годин з 168, прогони 00 і 12 UTC усі 168; 6 з 681 прогонів коротші з вини джерела (таблиця в [weather_runs.md](data/silver/weather_runs.md), розділ Пастки).
- Якщо `hourly_units` змінилися, зупинитися.
- Для моменту t брати найсвіжіший прогін з `available_at_utc < t`; порожнє значення брати зі старшого прогону.

**Витік:** час доступності `available_at_utc = run_utc + 8 год` (фактична затримка 6.4 год плюс запас). З правилом `< t` випередження прогнозу 9-14 год, до 20 год у 6 годинах після пропущеного прогону 2026-06-10T12:00. `fetched_at_utc` не час доступності: бекфіл забирає все сьогодні.

**Пастки:**
- Прогону 2026-06-10T12:00 в архіві нема (HTTP 400).
- Після вибору прогону порожні 42 значення з 3906 годин (вітер і напрям по 12, опади, пориви і видимість по 6); усі закриває старший прогін.
- Це вузол моделі, не станція; видимість модельна (80..55 200 м у всіх прогонах).
- Вітер у км/год, не м/с.

**Перевірка:** скрипт на прогонах 2026-10-09T12:00 і 2026-10-10T06:00 дає 336 рядків, непорожніх хмарності і видимості по 313, рядок години 2026-10-10T12:00 як у прикладі вище. Повний бекфіл прогонів 2026-04-30T00:00..2026-10-10T06:00 дав 653 файли і 109 704 рядки CSV. Для 3906 годин від T0 до 2026-10-10T14:00Z вибраний за правилом прогноз (з добором зі старшого прогону) має: хмарність 0..100 %, опади 0..6.1 мм, вітер 0..25.8 км/год, пориви 2.5..64.4 км/год, напрям 1..360, видимість 620..54 940 м, порожніх 0.

**Відкрите рішення:** Open-Meteo безкоштовно лише некомерційно; для шкільного проєкту підходить, для комерційного потрібен платний план.

## 4. Астрономія

**Що збираємо:** для Києва (50.4501, 30.5234) погодинно: висота Сонця, темно чи ні (цивільні і навігаційні сутінки), освітленість і фаза Місяця; щодня: схід і захід Сонця, сутінки, тривалість дня і ночі. Рахуємо локально, без мережі.

**Джерело:** власний модуль `kyiv_astro.py` на stdlib: рівняння NOAA Solar Calculator (Meeus) для Сонця, Meeus «Astronomical Algorithms», розділ 48, для фази Місяця. Контроль: MET Norway Sunrise 3.0 (https://api.met.no/weatherapi/sunrise/3.0/) і каталог фаз Espenak (https://astropixels.com/ephemeris/phasescat/phases2001.html).

Чому не бібліотека: skyfield, ephem і astral не встановлені, а нова залежність лише з «так». Автор ephem радить замінити його на Skyfield; astral 3.2 без релізів з 2022 і без освітленості Місяця; skyfield 1.55 потребує файл ефемерид de421.bsp (16.8 МБ). Точності формули для погодинних ознак вистачає (див. Перевірку).

Код: [scripts/bronze/kyiv_astro.py](../scripts/bronze/kyiv_astro.py) (stdlib, перевірено).

**Як:** `python3 -I scripts/bronze/kyiv_astro.py build data/bronze/astro`. Таблиці рахуються з 2026-04-30 до 2026-10-12; для інших дат змінити `d0` і `d1` у `build`.

**Формат і куди** (усі часи UTC з `Z`, `date_kyiv` = місцева дата):
- `data/bronze/astro/kyiv_astro_daily.csv`: `date_kyiv, sunrise_utc, sunset_utc, civil_dawn_utc, civil_dusk_utc, nautical_dawn_utc, nautical_dusk_utc, astro_dawn_utc, astro_dusk_utc, day_length_h, night_civil_h, night_nautical_h, moon_illum_midnight, moon_phase_midnight`.
- `data/bronze/astro/kyiv_astro_hourly.csv`: `hour_utc, sun_alt_deg, dark_civil, dark_nautical, moon_illum, moon_phase`.

**Правила:** схід і захід = центр Сонця на -0.833° (рефракція і радіус), сутінки = -6, -12, -18°. `dark_civil` = висота < -6°, `dark_nautical` < -12°. `moon_phase`: 0 новий Місяць, 0.25 перша чверть, 0.5 повня, 0.75 остання чверть; `moon_illum` = частка освітленого диска. Денні значення Місяця на київську північ наприкінці `date_kyiv`.

**Витік:** немає, усе відомо наперед; з іншими даними з'єднувати за `hour_utc` або `date_kyiv`.

**Пастки:**
- Білі ночі: астрономічна ніч (-18°) у Києві не настає з кінця травня до середини липня. `astro_dawn_utc` порожній у 48 рядках (05-29..07-15), `astro_dusk_utc` у 49 (05-23 і 05-29..07-15); 05-24..05-28 сутінки настають після київської півночі і пишуться на наступну дату. Тому темряву міряємо цивільними і навігаційними сутінками.
- Потрібна tzdata з назвою `Europe/Kyiv` (2022b+).
- Схід і захід Місяця модуль не рахує.

**Перевірка:** `python3 -I scripts/bronze/kyiv_astro.py day 2026-10-10` друкує:

Точність: схід і захід проти MET Norway +0.0..+0.9 хв на 3 датах; 50 фаз Місяця 2026 проти Espenak: похибка моменту до ~0.8 год, у середньому 0.29 год.

**Відкриті рішення:** лишаємо формулу без залежностей (обрано) чи ставимо skyfield (потрібне «так»); чи потрібна ознака «Місяць над горизонтом» (тоді простіше skyfield).

import datetime as dt
Y = 2026
def nth(n, wd, m):  # n-th weekday (0=Mon..6=Sun) of month m
    f = dt.date(Y, m, 1); return f + dt.timedelta((wd - f.weekday()) % 7 + 7 * (n - 1))
def last(wd, m):  # last weekday of month m (m < 12)
    l = dt.date(Y, m + 1, 1) - dt.timedelta(1); return l - dt.timedelta((l.weekday() - wd) % 7)
def orth_easter(y=Y):  # Meeus: Julian date + 13 days (valid 1900-2099)
    a, b, c = y % 4, y % 7, y % 19; d = (19 * c + 15) % 30; e = (2 * a + 4 * b - d + 34) % 7
    m, r = divmod(d + e + 114, 31); return dt.date(y, m, r + 1) + dt.timedelta(13)
E = orth_easter()
print("easter", E, "trinity", E + dt.timedelta(49), "kyiv_day", last(6, 5), "ru_navy", last(6, 7),
      "ru_pvo", nth(2, 6, 4), "ua_repr", nth(3, 6, 5), "ua_navy", nth(1, 6, 7), "ua_af", nth(1, 6, 8),
